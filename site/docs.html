Start

Overview

Hoodwink checks tokens on Robinhood Chain (chain id 4663) and answers the questions that decide a trade on Pons: is this the original ticker, are the links real or borrowed, who is the deployer and what did they do before, are the snipers still holding, how much do the top 10 own, and, taking all of it together, is this a real product, an honest meme or a LARP.

Why not a contract scanner

Almost every token on Robinhood Chain is launched on Pons, and every Pons token is the same audited template: fixed supply, no mint, no blacklist, no pause, and selling always works through the curve or the Uniswap v4 pool. A scanner that reads the contract will mark every one of them safe. Hoodwink still verifies that (one line, contract), and spends the rest of the report on what actually differs from token to token: the story and the wallets.

What a report contains

  • Identity: ticker uniqueness against every Pons launch, look-alikes of Robinhood stock tokens, Robinhood branding, the pair asset.
  • Reality: the website, X and GitHub links typed at launch (read from the launch transaction), each one opened and checked, then an AI verdict written from that evidence.
  • Launch: what was bought in the launch block and the first 30 seconds, whether those wallets still hold, whether they were throwaway wallets.
  • Holders: the top 10 wallets with exact balances, and groups of wallets that pass tokens between themselves.
  • Developer: what the deployer did on this token, and the track record of every earlier Pons launch from the same wallet.
  • Market and contract: liquidity, and the one-line contract verdict.

What it is not

A report describes a token; it does not certify it, and the coverage percentage is not a safety score. See what a scan cannot tell.

How a scan works

Two halves run at the same time. Your browser reads the chain directly; the Hoodwink server opens the links (a browser is not allowed to read third-party sites) and asks the AI for a verdict.

address
  │
  ├─ browser ── chain (public RPC)
  │    ├─ token, Pons factory record, launch event and block
  │    ├─ every Transfer since launch → snipers, fresh wallets, top 10, linked wallets
  │    ├─ every earlier launch by the deployer → graduated? dumped? how fast?
  │    ├─ ticker index (static files) + launches since the index was built
  │    └─ contract: template diff + simulated buy, transfer, sell (eth_call)
  │
  └─ server ── /api/reality  (cached 6 h)
       ├─ launch transaction → description, website, X, Telegram, GitHub typed at launch
       ├─ website: fetched with redirects, shortener / builder detection, contract address present?
       ├─ X: post read through X's public embed endpoint (author, date, text)
       ├─ GitHub: repository age, commits, fork, last push
       └─ /api/verdict  (cached 24 h) → AI reads that evidence only → real product / honest meme / LARP

How long it takes

A young token settles in 10 to 30 seconds; the AI verdict adds a few seconds the first time a token is judged and nothing after that (cached). Tokens with 100,000+ transfers take one to three minutes, spent reading logs.

Quickstart

In the browser

Open the scanner, paste a token address, press Scan. The report URL (scan.html?a=0x…) is shareable: whoever opens it runs the scan again on the block they open it.

From a terminal

The CLI runs the exact module the site runs. Node 18 or later, no dependency to install.

git clone <repository> hoodwink && cd hoodwink
node tools/scan.mjs 0x07ebb29a38fbcb41563817e5e19f2cec619c90d2
node tools/scan.mjs 0x07ebb29a38fbcb41563817e5e19f2cec619c90d2 --json bun.json

Using another RPC

Set rpc in config.js, or call setRpc(url) before investigate(). The endpoint must allow CORS for browser use and support eth_call state overrides.

The 16 checks

Each check answers one question and returns a status (see statuses and coverage). Thresholds are listed so you can disagree with them.

Identity

CheckHow it decides
tickerThe normalised ticker (case, $ and punctuation ignored) is looked up in the index of every Pons launch, plus launches since the index was built. Only one: pass. This is the first of several: info. A later copy: concern; a copy of a token that graduated, by another wallet: critical. See ticker index.
stockName says "Robinhood Token" but the code is not the official stock proxy: critical. Ticker of one of the 78 stock tokens: concern, with the address of the real one.
brand"Robinhood" or "Hood Chain" in the name, or tickers RH / HOOD / RHC: concern. Robinhood Chain has no native token.
pairETH, USDG or an official stock: pass. A stock ticker that fails the fingerprint: critical. Another memecoin: concern.

Reality

CheckHow it decides
websiteNone: info. Dead, error or unreachable: concern. Live and shows this contract address, no other flag: pass. Live without the contract: info; plus a shortener, a JavaScript-only page or an X link that differs from the one typed at launch: concern.
socialThe X link is a post by another account: concern, critical if a major or business-verified account (borrowed narrative). A profile the website also links: pass; a different one: concern; not cross-checkable: info.
codeNo repository: info. Missing repo, nearly empty (under 5 commits) or a thin fork: concern. Created after launch: info. Real history before launch: pass.
larpThe AI verdict. LARP: critical. Unclear: concern. Honest meme or real product: pass. See reality checks and AI verdict.

Launch

CheckHow it decides
firstblockWindow = launch block + 287 blocks (30 s). Other transactions in the launch block above 10% of supply, or early buyers still holding above 20%: critical. Launch block above 3%, first 30 s above 12%, or still holding above 8%: concern.
burnersUp to 40 early buyers; fresh = plain wallet with lifetime nonce 3 or less. Above 50% fresh (4+): critical. Above 30% (3+): concern.

Holders

CheckHow it decides
distributionExact balances (balanceOf). Pools and contracts set aside, smart-account wallets counted. Largest above 15% or top 10 above 50%: critical. Above 6% / 30%: concern.
clustersWallets that sent the token to each other are grouped; hubs with 20+ counterparties ignored. Group above 15%, or with the deployer above 5%: critical. Above 5%: concern.

Developer

CheckHow it decides
devOn this token: sold 80%+ of more than 1% received, spread more than 2% to other wallets, or still holds more than 10%: concern.
devrepSee deployer track record. Three or more dumps and a dump rate of 60%+: critical. Ten or more earlier launches, or two dumps: concern. At least one graduation and a dump rate below 50%: pass. First launch: info.

Market and contract

CheckHow it decides
liquidityCurve reserves and real balance, or the Uniswap v4 pool state. info.
contractFolds nine measurements into one line: code present, ERC-20 interface, proxy, owner, 56 privileged signatures, Pons template diff, origin, a simulated buy-transfer-sell (probe) and taxes. On a standard Pons token this is a pass; otherwise it takes the worst status found and lists why.

Statuses and coverage

StatusMeaning
PassThe specific thing measured is fine. Only that thing.
InfoA fact worth knowing that is neither good nor bad on its own.
ConcernRead this before buying. Not proof of bad intent.
CriticalA strong signal against the token: copied ticker of a winner, borrowed narrative, serial dumper, LARP verdict, bundled launch.
UncheckedThe question could not be answered (server down, data too large, no metadata). Never counted as a pass.
N/AThe question does not apply. Left out of the coverage.

At a glance

The top of every report sums the findings up in one card: a risk level (High risk if any check is critical, Caution if any is a concern, Low risk otherwise), one sentence that lists the risks in order of severity and what came out clean, and eight tiles: ticker, website, X account, tech and claims (the AI verdict), snipers, top 10, developer and contract. It fills in live while the scan runs. Every tile is backed by a check further down.

Coverage

coverage = settled checks ÷ applicable checks. It says how complete the investigation is, never how safe the token is.

Reference

Reality checks and AI verdict

When a token is launched on Pons, everything the creator typed (name, ticker, logo, description, website, X, Telegram, Discord, Farcaster, GitHub) travels in the launch transaction. Routers wrap the factory call differently, so instead of one ABI the calldata is scanned for ABI-encoded strings, which are then sorted into fields.

How each link is checked

  • Website. Fetched by the server with up to five redirects, each one re-checked; private and internal addresses are refused, pages are capped at 1.5 MB and 8 seconds. Measured: HTTP status, final URL, link shortener, site builder (Linktree, Carrd, Notion, Framer…), readable text, whether this exact contract address appears, and which X, GitHub and Telegram links the page contains.
  • X. A profile link is compared with the X link on the website. A post link is read through X's public embed endpoint: author, date, text. A post by someone else (for example @RobinhoodApp) is reported as borrowed narrative.
  • GitHub. From the launch metadata, or the first repository linked on the website: existence, creation date versus launch date, commit count, fork or not, last push.

The AI verdict

The evidence above is written into a short file and sent to Claude (claude-opus-5-5, structured JSON output). The model answers with one of four verdicts, a confidence, a one-line headline, each claim the project makes with the evidence that supports or fails it, and red and green flags.

VerdictMeaning
Honest memeNo product, team or affiliation claimed. Normal, not negative.
Real productA product is claimed and the evidence shows it exists.
LARPA product, AI agent, protocol, affiliation or team is claimed, and the evidence is missing, dead, borrowed or contradicts it.
UnclearNot enough evidence either way.

Safeguards

  • The verdict endpoint takes only a token address. The evidence is gathered by the server itself, so nobody can make the AI judge text they wrote into the request.
  • Website, description and post text are passed as untrusted data; the instructions tell the model never to follow instructions found in them.
  • One verdict per token per 24 hours (cached), and a daily cap (VERDICTS_PER_DAY, 400 by default) bounds the API bill.
  • No request waits on the model: /api/verdict answers at once with the cached verdict or { pending: true }, a background function does the work, and the page polls every two seconds. A slow model can never time a request out.
Reference

Ticker index

A static index of every Pons launch lives in data/tickers/: one file per first two characters of the normalised ticker, each entry [token, launchBlock, symbol, name, deployer], plus meta.json with the last indexed block and the total.

On the home page, typing a ticker ($REX or rex) instead of an address lists every Pons token using it, the first launched marked as the original, each one a click away from its report.

When a scan runs, the browser loads one shard, then reads every launch made since meta.json's block straight from the chain (up to the latest 8,000) and their tickers through Multicall3, so a copy launched five minutes ago is still caught.

node tools/build-index.mjs            # full rebuild (about ten minutes)
node tools/build-index.mjs --update   # only launches since the last build

Keeping it fresh

Nothing to do by hand. A scheduled function (tickers-update, hourly) appends every new launch to a tail stored in the cache, served by /api/tickers-tail?shard=XX; a scan reads the static shard, then the tail, then only the last few minutes live. Locally, launch.bat runs the same job every hour while it is open. Rebuild the static files now and then (node tools/build-index.mjs --update, then redeploy) to keep the tail small.

Reference

Deployer track record

Every Pons launch event carries the deployer as an indexed topic, so all launches by a wallet come back in a dozen log queries. For each earlier launch (the latest 30):

  • Graduated: read from the Pons factory record and the curve.
  • Dumped: the deployer sent 80% or more of everything it received of that token to the token's curve or the v4 pool manager. The delay is measured from the launch block to the first such sell.

The summary reads like "14 earlier Pons launches: 2 graduated, 9 dumped by the deployer (median 1.8 min after launch)", and every launch is listed with a link.

Known developers

data/devs.json maps a deployer address to a label, a tone (good, bad or neutral), a note and a source. A label overrides the computed status and is always shown with its source. The file ships empty: add entries only with a public source.

{ "0xabc…": { "label": "Team behind X", "tone": "good", "note": "Shipped Y", "source": "https://…" } }

Limits

A new wallet has no history; a careful deployer uses a fresh one each time. Funding links between wallets (who sent the ETH) are not traced: the public RPC has no index for it.

The probe contract

The round trip is executed by a small Solidity contract, Probe.sol. It is never deployed. The scanner sends an eth_call whose state override places the probe's runtime bytecode at 0x4000…0d0d, gives that address 100 ETH (and, for USDG or stock pairs, a balance written straight into the pair token's storage), then calls one function. The node executes it against the latest block and throws the result away.

Stages

StageWhat happensFailure means
1 · Buycurve.buy(), or PoolManager.unlock() → swap() exact-in → settle() → take()Buying is blocked at this block
2 · Movetransfer() of 25% to 0x…beef; the fresh wallet's balance delta is measuredTokens cannot leave a wallet: a trap
3 · Sellcurve.sell() or the reverse swap, with the remaining balanceHoneypot behaviour
4 · CompleteQuote returned, compared with the quote spent for the share sold

Every external step is wrapped in try/catch, so a revert comes back as a stage number with its revert data, not as a failed request.

Tokens without a venue

For stock tokens and non-Pons tokens the probe is funded through the token's own balance storage (the slot is discovered by trying mapping slots 0 to 11 and the OpenZeppelin ERC-7201 namespace) and runs holderMove(). If no slot is found, the probe's code is placed on the address of a real holder that is a plain wallet, which then moves part of its own balance.

Batch reads

codeSizes(address[]) returns the code size and code hash of up to 1,500 addresses in one call. It is how the scanner tells wallets, smart accounts and contracts apart without one request per address.

Source

Compiled with solc 0.8.26, optimizer 200 runs. Download Probe.sol.

Stock-token fingerprint

Robinhood issues each tokenized stock as a 283-byte beacon proxy. The bytecode is identical for every stock: the issuer's beacon address is compiled into it as an immutable, and the proxy asks the beacon for its implementation on every call.

FieldValue
Runtime code hash0x6c1fdd40002dcb440c7fff6a84171404d279ccb057803b65826f7546acd65630
Beacon (immutable)0xe10b6f6b275de231345c20d14ab812db62151b00
Name pattern<Company> • Robinhood Token
Measured onNVDA, TSLA, AAPL, then all 78 stock tokens used as Pons pair assets

How look-alikes are judged

  • Fingerprint matches: genuine. Issuer powers (upgrade through the beacon, mint, pause) are shown as info: they are expected for a regulated asset, and they are real.
  • The name claims "Robinhood Token" and the fingerprint does not match: critical, impostor.
  • Only the ticker matches: concern. A memecoin called MU is not a crime, but someone looking for Micron should know this is not it.
  • As a pair asset, a stock ticker that fails the fingerprint is critical: buyers would be paying in a copy.

Running and deploying

On your machine

Double-click launch.bat (or node serve.mjs 6912): it serves the site and the /api/* functions, then opens the browser. Put the keys in a .env file next to it (copy .env.example).

VariableUse
ANTHROPIC_API_KEYEnables the AI verdict. Read from the environment, or from netlify/lib/secrets.mjs (server-only, git-ignored, bundled into the functions at deploy). Without it, everything else works and the verdict shows as unchecked.
GITHUB_TOKENOptional. Raises the GitHub API limit from 60 to 5,000 requests per hour.
VERDICTS_PER_DAYOptional. Daily cap on new AI verdicts (default 400).
RH_RPCOptional. Another Robinhood Chain RPC for the server.

On Netlify

netlify.toml publishes site/ and deploys netlify/functions/; the cache uses Netlify Blobs. Set the variables above in the site settings. Run npm install once so the functions have their dependencies.

Cost of the AI verdict

About 3,000 input tokens and a few hundred output tokens per new token, at low effort: roughly one US cent per verdict at Claude Opus 5.5 prices, and nothing for the 24 hours after (cached).

Data sources and limits

One source

Everything comes from the public Robinhood Chain JSON-RPC: eth_getCode, eth_getStorageAt, eth_call (with state overrides), eth_getLogs, eth_getTransactionCount, eth_getBlockByNumber. No indexer, no explorer API, no price feed, no off-chain list except the stock tickers, which were themselves read from the chain. Explorer links in reports are for your convenience; nothing is read from them.

Limits of the RPC, and what the engine does about them

LimitEffectHandling
eth_getLogs spans at most 10,000,000 blocksA full history needs about 11 windowsWindows read one at a time, oldest first, so a cap always keeps the launch
eth_getLogs returns at most 10,000 eventsBusy windows failSplit in halves recursively, up to 18 levels
Historical state for about 100,000 blocks onlyBalances at launch cannot be readRebuilt from events; current balances read with balanceOf
No tracing (debug_traceCall)Internal calls are not visibleThe probe reports stages and balance deltas instead
Rate limits429 or "too many requests"6 requests in flight, exponential back-off, retries

The 60,000-transfer cap

Above 60,000 transfers the browser would hold too many events. The engine then keeps the launch window and the latest 20,000 transfers, reads exact balances for every wallet in them, and labels the affected checks as covering that range.

Trust

What a scan cannot tell

Read this page once. It is the difference between using Hoodwink well and trusting it too much.

  • The future. The round trip proves a buy and a sell work at this block. A token whose rules can change (owner, proxy, beacon) can stop working tomorrow; that is why those powers are reported separately.
  • Roles other than owner. The privileged-function scan sees functions, not who may call them. A renounced owner with a separate admin role is possible; the summary says "unless they use a role other than owner" for that reason.
  • Intent. A deployer who sold is not necessarily a rug; a clean launch is not a promise. The report describes behaviour.
  • Off-chain links. Wallets funded by the same exchange account, or coordinated in a chat, look independent on chain. Clusters only see direct token transfers.
  • Unknown launchpads. Tokens not launched on Pons get fewer checks (no launch record, no curve). Those checks are marked unchecked, not passed.
  • Price. Hoodwink does not say whether a token is cheap, expensive or going anywhere.

Trust assumptions

You trust the RPC to return the chain's real state, and you trust this engine's code, which is short enough to read. To remove the first assumption, point setRpc() at your own node.

FAQ

Does Hoodwink need my wallet?

No. There is no connect button. A scan only reads.

Is a 100% coverage report safe?

No. It means every applicable question was answered. Read the answers.

Why does a scan take two minutes for some tokens?

Tokens with long histories need many log requests, because the RPC caps each one at 10,000 events. Young tokens take seconds.

Why is a stock token's mint power only "info"?

Because the issuer mints and redeems shares by design. It is still shown, so that you know it exists.

Can the probe spend real money?

No. It exists only inside a read-only call. The 100 ETH it holds are written into that call's imaginary state.

Which launchpads are supported?

Pons, fully. Any ERC-20 gets identity, control, distribution and a transfer test. More launchpads will be fingerprinted; the changelog will say when.

Why not a single safety score?

Because it would hide the one finding that matters to you behind an average.

Do I need an API key?

Not to use the site. Whoever runs the server sets one Anthropic key for the AI verdict; everything else needs no key at all.

Can a project game the AI verdict?

It can write anything on its website, and the model is told to treat that text as a claim to verify, never as an instruction. What it cannot fake is the rest of the file: a dead link, a post by someone else, a repository created yesterday, a deployer who dumped nine launches.

Is this affiliated with Robinhood?

No. Hoodwink is an independent tool that reads a public chain.
